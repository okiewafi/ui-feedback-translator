# 回饋協議

## 四個操作

### 1. 開工前 spec 確認
回開工確認：anchor、使用的 tokens、頁面清單、edge-state checklist。
設計負責人批准才動。沒 spec 不開工。

### 2. 生成時 self-validate
每張輸出交件前跑 `bin/validate.py`。不過的自己重畫，不交件。
偏離 spec 的地方主動宣告原因，不要等被抓。

### 3. 回饋時意圖複述
收到回饋後，先翻成 spec diff，複述確認，再重畫。
把會錯意的成本從「重畫一輪」降成「一句話」。

spec diff 格式：
```
# 機械變更
- {element: "primary-button", token: "leading", from: "spacing-4", to: "spacing-3", round: 3}
# 品味變更
- {region: [x, y, w, h], note: "感覺太擠", type: "taste", round: 3}
```
每條帶 round id，對應到第幾輪 review，避免多輪並行時對錯版。

### 4. 品味題變體策略
品味回饋一律出 2–3 個變體讓設計負責人選，不賭單一答案。

## 回饋語言

- **機械回饋講解法**（對錯客觀）：token 語言。
  「X 元件的 leading 從 spacing-4 改 spacing-3。」不說「往左一點」。
- **品味回饋講問題**（解法不唯一）：位置 + 感受，不講解法。
  「這裡感覺擠」+ 圈選位置。不說「把這個往左移 8pt」。
- 分工：人負責發現問題，AI 負責出解法（變體），人負責選。

## 品味的邊界

- 手勢/圈選只解決局部品味。全局品味（整頁節奏、左右輕重）
  用變體挑選，不用手勢表達。
- 品味迭代的來回是設計本身，不是浪費。目標是把每一輪
  花在品味上，而不是花在修間距上。
